# go-legado-demo 动态网页抓取说明

本文档说明：当书源页面依赖 JavaScript 异步加载时，如何在 Go 中获取「渲染完成后的页面源码」，以及在本项目中的推荐方案与跨平台部署要点。

相关文档：[书源配置说明.md](./书源配置说明.md)

---

## 1. 背景与问题

### 1.1 当前实现

`main.go` 中的页面抓取走标准 HTTP 客户端：

- `fetchText(url)`：普通 GET
- `fetchTextWithRule(raw)`：支持 `URL,{method,body,headers}` 扩展配置

搜索、详情、目录、正文等接口最终都依赖上述函数拿到响应文本，再按书源规则解析。

### 1.2 局限

`net/http` **只接收服务端返回的原始响应**，不会：

1. 执行页面里的 JavaScript
2. 等待 AJAX / fetch 请求完成
3. 等待 DOM 被脚本动态插入

因此，对于 **SPA（React/Vue 等）** 或 **正文由 JS 注入** 的站点，直接 GET 往往只能拿到空壳 HTML，规则解析结果为空。

### 1.3 目标

在 **Windows** 与 **Linux 无桌面终端** 环境下，稳定获取「异步加载完成后的完整 HTML」，供现有规则引擎继续解析。

## 2. 方案对比

| 方案 | 能否等 JS 渲染 | 跨平台 headless | 依赖体积 | 推荐度 |
|------|----------------|-----------------|----------|--------|
| `net/http`（现有） | ❌ | ✅ | 极小 | 默认首选 |
| 直接请求站点 API | 视站点而定 | ✅ | 极小 | 有 API 时优先 |
| **rod** | ✅ | ✅ | 小 | ⭐ **推荐** |
| chromedp | ✅ | ✅ | 小 | 可选 |
| playwright-go | ✅ | ✅ | 大 | 复杂自动化时用 |

### 2.1 为什么推荐 rod

1. **跨平台省心**：`launcher` 可按操作系统自动查找或下载 Chromium，Linux 服务器不必手动配路径。
2. **API 直观**：`WaitLoad`、`WaitVisible` 等语义清晰，便于按书源定制等待条件。
3. **体量合适**：本项目大部分书源仍走 HTTP，仅少数 JS 源需要浏览器；rod 比 playwright-go 更轻。

### 2.2 何时不必上浏览器

优先尝试以下方式，再考虑 headless：

1. 站点有公开 JSON / XHR 接口 → 在 `searchUrl` 或规则里直接请求 API（参见 [书源配置说明.md](./书源配置说明.md) 案例二）
2. 正文已在首屏 HTML 里 → 继续用现有 `fetchTextWithRule`
3. Legado 书源里的 `@js:` 逻辑可在服务端用 `goja` 复刻（本项目已引入 goja）

## 3. 推荐架构（接入规划）

建议在现有抓取层增加「双通道」：

```txt
fetchPage(rawURL)
  ├─ 默认 → fetchTextWithRule（现有 HTTP 逻辑）
  └─ 书源标记需 JS 渲染 → headlessFetch（rod headless）
```

书源侧可通过扩展字段或约定前缀区分，例如：

```txt
browser:https://example.com/chapter/123
```

或在书源 JSON 中增加可选字段（接入时再定）：

```json
{
  "bookSourceName": "示例JS源",
  "needBrowser": true,
  "browserWaitFor": "#chapterContent"
}
```

正文、目录等解析规则 **无需改动**，headless 只负责返回完整 HTML 字符串。

## 4. rod 最小示例

### 4.1 安装

```bash
go get github.com/go-rod/rod
```

### 4.2 获取渲染后 HTML

```go
package fetcher

import (
    "os"
    "time"

    "github.com/go-rod/rod"
    "github.com/go-rod/rod/lib/launcher"
)

func HeadlessHTML(url, waitSelector string, timeout time.Duration) (string, error) {
    path := os.Getenv("CHROME_PATH")
    if path == "" {
        path = launcher.New().Browser().MustGet()
    }

    l := launcher.New().
        Bin(path).
        Headless(true).
        Set("disable-gpu").
        Set("no-sandbox").              // Linux 容器 / root 用户常需要
        Set("disable-dev-shm-usage")    // Docker 内存较小时建议开启

    u := l.MustLaunch()
    browser := rod.New().ControlURL(u).MustConnect()
    defer browser.MustClose()

    page := browser.Timeout(timeout).MustPage(url)
    page.MustWaitLoad()

    if waitSelector != "" {
        page.MustElement(waitSelector).MustWaitVisible()
    }

    return page.MustElement("html").MustHTML(), nil
}
```

### 4.3 等待策略说明

| 方法 | 适用场景 |
|------|----------|
| `MustWaitLoad()` | 等 `load` 事件，适合大部分页面 |
| `MustElement("#id").MustWaitVisible()` | 正文容器由 JS 延迟插入 |
| 固定 `Sleep` | 仅作兜底，不推荐作为主策略 |

`load` 事件 **不等于** 所有 XHR 结束。若正文仍为空，应改为等待具体 CSS 选择器（与书源 `ruleContent` 对应节点一致最佳）。

## 5. Windows 部署

### 5.1 浏览器来源

任选其一：

1. 本机已安装的 Google Chrome / Microsoft Edge
2. rod `launcher` 自动下载的 Chromium（首次约 100–150 MB）

### 5.2 环境变量（可选）

```powershell
$env:CHROME_PATH = "C:\Program Files\Google\Chrome\Application\chrome.exe"
```

不设置时，rod 会尝试自动发现或下载。

### 5.3 注意

- 杀毒软件可能拦截 Chromium 下载或启动，需加白名单
- 开发机可临时关闭 headless 调试：`Headless(false)`（生产环境务必 headless）

## 6. Linux 无 UI 部署

### 6.1 原则

- **不需要** X11、Wayland 或桌面环境
- 必须 **headless** 模式
- 容器内常需 `--no-sandbox`、`--disable-dev-shm-usage`

### 6.2 Debian / Ubuntu 安装 Chromium

```bash
apt-get update
apt-get install -y chromium \
  ca-certificates fonts-liberation libasound2 libatk-bridge2.0-0 \
  libatk1.0-0 libcups2 libdbus-1-3 libdrm2 libgbm1 libgtk-3-0 \
  libnspr4 libnss3 libxcomposite1 libxdamage1 libxfixes3 libxrandr2
```

```bash
export CHROME_PATH=/usr/bin/chromium
```

### 6.3 Docker 示例片段

```dockerfile
FROM debian:bookworm-slim

RUN apt-get update && apt-get install -y --no-install-recommends \
    chromium ca-certificates fonts-liberation \
    libnss3 libgbm1 libgtk-3-0 libx11-xcb1 \
    && rm -rf /var/lib/apt/lists/*

ENV CHROME_PATH=/usr/bin/chromium
```

建议给容器至少 **512 MB** 内存；并发抓取时需更多，并限制同时打开的 tab 数量。

### 6.4 常见报错

| 现象 | 处理 |
|------|------|
| `Running as root without --no-sandbox` | launcher 加 `Set("no-sandbox")` |
| 页面崩溃 / 超时 | 加 `disable-dev-shm-usage`，增大 `/dev/shm` 或内存 |
| `error while loading shared libraries: libnss3.so` | 安装 `libnss3` 等依赖（见 6.2） |
| Alpine 镜像缺库 | 改用 Debian/Ubuntu 基础镜像，或自行补齐全部依赖 |

## 7. 生产环境建议

1. **浏览器进程复用**：不要每个章节请求都 `MustLaunch()` 新浏览器；维护单例或池化 Browser，只新建 Page。
2. **超时**：单次抓取建议 15–30 秒上限，避免慢站拖死服务。
3. **并发限制**：headless 内存占用高，建议单独信号量（如最多 2–4 个并发 Page）。
4. **降级**：headless 失败时可记录日志并 fallback 到 HTTP（便于对比 `debug_logs` 里的 raw 响应）。
5. **优先 API**：新接书源时先抓包看 XHR，能 HTTP 直连接口就不要开浏览器。

## 8. 与 debug_logs 的配合

现有调试流程（见 [书源配置说明.md](./书源配置说明.md) 第 9 节）：

1. 对比 `*_raw.html` / `*_raw.txt` 与解析结果
2. 若 raw 几乎是空壳、但浏览器里能看到正文 → 该书源适合走 headless
3. 若 raw 已有完整正文 → 继续 HTTP 即可，无需引入 rod

## 9. 常见问题

**Q：`net/http` 算「一步」完成吗？**  
A：算，但拿不到 JS 渲染后的 DOM。

**Q：rod 算「一步」吗？**  
A：对外可封装成一个函数调用；内部会启动浏览器、导航、等待、取 HTML。

**Q：Windows 和 Linux 能用同一套代码吗？**  
A：可以。通过 `CHROME_PATH` 或 rod 自动发现浏览器，headless 参数两边一致。

**Q：会不会比 Legado App 里 WebView 慢很多？**  
A：通常更慢、更耗内存。仅对确实需要 JS 的源启用。

**Q：漫画源（`bookSourceType=2`）需要吗？**  
A：若图片 URL 已在 HTML 或 API 里，不需要；若图片列表由 JS 动态生成，才需要 headless 或改抓 API。
